The Builder's Workbench / Local-first engineering

Safe saves.

Why a file that looks saved can still break — and how to replace it without showing readers a half-written document.

FOUNDATION, NOT NEWS10-MIN READ20-MIN LABREVIEWED SOURCE · NO WEBSITE
≠ATOMIC is not DURABLE.

A clean handoff is different from surviving a power loss. Build for both deliberately.

For PDF editors, note apps, project settings and any local-first product.No APIs · No packages · Original illustrations

01 / Why it matters

Your save button has two jobs.

Imagine a user edits a 60-page document. The app opens the original file, truncates it, and writes the new bytes directly. If the process stops midway, the next launch may find neither the old complete document nor the new one. That is a partial-write failure.

The fragile move

Write onto the only copy.

The destination becomes incomplete before the new version is ready. A failed save can turn yesterday's good data into unusable bytes.

The safer move

Prepare a replacement elsewhere.

Write and sync a sibling temporary file, then swap its name into place. Under POSIX local rename semantics, readers see the old or new pathname target — not an in-between truncation. [P1, L1]

One-paragraph answerFor a single file in a trusted local directory, prepare the whole next version in a temporary sibling, flush and sync it, atomically replace the old pathname, and try syncing the parent directory. This reduces torn-file exposure during ordinary interruptions. It does not solve multi-writer conflicts, remote synchronization, permissions, backups or unreliable storage by itself.

02 / Start with the vocabulary

Four words that should never blur together.

01 · Atomic visibility

Old or new.

A successful supported rename swaps the target path as a unit. Existing open file handles may still read an older inode or snapshot. [L1]

02 · Durability

Still there after a crash.

Buffered writes may be pending. flush() followed by fsync() requests a disk sync; actual guarantees depend on OS, filesystem and hardware. [P2]

03 · Isolation

No writer steps on another.

Two editors can each save a complete file yet silently overwrite one another. Atomic replacement alone does not coordinate them.

04 · Recovery

You can undo loss.

A last-known-good snapshot or tested backup is a separate safety layer. Atomic saves do not recover an intentional bad edit, deleted document or corrupt storage.

03 / Visual mechanism

05 / Where it breaks

Five traps the green unit tests won't catch.

Trap 01 · Storage

A rename is not a battery.

Some disks, filesystems or network shares do not honor all durability assumptions. File fsync() and directory fsync() are requests, not evidence of every physical cache state. [P2, L1]

Trap 02 · Conflict

Last writer wins.

Two editors can generate valid but conflicting complete snapshots. Add locks, version checks with a real compare-and-swap protocol, or a transactional database; this code does not do it.

Trap 03 · Metadata

Mode and ACLs can change.

Replacing a file substitutes a newly created inode or file object. Existing ownership, permissions, extended metadata and open handles need deliberate treatment.

Trap 04 · Trust boundary

Names can be attacked.

A malicious process can race paths or replace directory entries. The lab assumes one trusted directory; a hardened production implementation needs platform-specific descriptor and sandbox design.

Trap 05 · No undo

A valid bad save still wins.

The new bytes can be syntactically wrong or unwanted. Check document validity before replacement, keep recovery points, and test restore flows.

Alternative · Transactions

When one file is not enough.

SQLite offers atomic transactions, rollback journals and WAL, with defined concurrency and sync trade-offs. WAL supports readers during a writer, but only one writer at a time and not over a network filesystem. [S1, S2, S3]

These are engineering risks, not numerical failure-rate estimates. No power failure, multi-process race or Windows behavior was exercised by this lab.

06 / Work the problem

Three questions. Verify before you trust.

Try each answer before expanding the guidance. The goal is judgment, not memorizing the four system calls.

01 · The app stops after writing the temp file but before replacing the target. What should a user see?

The previous complete destination should remain at the target pathname in the single-writer, trusted-local-directory model. A leftover temp may remain after an abrupt process kill; the teaching code removes temps on catchable exceptions, but an OS kill bypasses Python's finally. A recovery routine must detect and validate leftovers without blindly trusting them.

02 · Why call flush() before fsync()? Does successful os.replace() prove a power loss is safe?

Python may buffer application bytes, so flush() submits them before the OS sync request. Rename atomicity concerns which file the pathname resolves to, not guaranteed power-loss durability. Storage semantics and directory metadata persistence still matter. [P1, P2]

03 · Two app windows each read version A, then save B and C. Does atomic replacement prevent lost updates?

No. Both writes can individually replace complete snapshots; the later pathname swap can erase the first editor's update. For coordinated records, use a transaction with concurrency control (for example, a database transaction or an application-specific version check under a lock). Atomic file replacement is not a multi-writer protocol.

07 / Field wisdom & what next

Protect the last good version until the next one is proven.

A clean swap solves one narrow problem very well. For a real local-first app, write down three explicit contracts: what readers are allowed to observe, what survives a process crash, and how the app recovers after a device interruption. Do not silently treat those as one guarantee.

Field ruleBefore you overwrite something irreplaceable, prove that the replacement is complete — and that you still know how to recover the previous version.
