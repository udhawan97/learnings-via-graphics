Why can a test pass alone but fail in the full suite?

Order changes the starting state. Find the smallest failing sequence, make each test own its setup and cleanup, then prove the suite works in both orders without retries.

ENGINEERING / THE BUILDER'S WORKBENCH · TESTINGFULL GUIDE: 9 MIN · PRACTICE: 20 MIN

01 · Visual model

A hidden handoff changes Test B

Text equivalent: B alone starts with the feature flag off and passes. A then B fails because A leaves the flag on. A reset before every test restores the off state, so both A then B and B then A pass.

02 · Read the evidence

Three runs turn a mystery into a boundary

RunResultWhat it tells you
B alonePassB can pass from a clean start.
A → BFailA, or state created while A runs, changes B's conditions.
B → APassThe dependency is directional; inspect what A leaves behind.

This pattern supports a shared-state hypothesis. It does not prove which boundary leaked, so inspect the narrowest candidates first.

03 · Shared boundaries

State hides in more places than globals

Process

Singletons, feature flags, environment variables, locale, timezone, fake clocks and random seeds.

Storage

Temporary files, fixed paths, database rows, browser storage, caches and snapshots.

Resources

Ports, server processes, threads, queues, locks and unfinished asynchronous work.

Framework

Broader-scoped fixtures, mocks, monkeypatches, registered hooks and mutated test doubles.

04 · Repair

Give every test an owned starting state

  1. Move required state into per-test setup or a function-scoped fixture.
  2. Register cleanup through the framework's guaranteed lifecycle, not only at the happy path's last line.
  3. Use unique temporary resources instead of fixed shared names.
  4. Wait for background work to finish and release its resources.
  5. Keep broader-scoped fixtures only when their state is immutable or explicitly reset.

Success criterion: B alone, A → B, B → A and the full suite all pass without retrying, sleeping or fixing the test order.

05 · Reality check

Order is not the only source of suite-only failure

  • Parallel workers can race for a port, file, database row or quota.
  • Time, randomness and external services can vary between runs.
  • Resource pressure can reveal a timeout or cleanup bug only in the full suite.
  • An overly strict assertion can fail at harmless numeric or timing boundaries.

Do not call retries a fix. A retry may reduce visible failures while preserving an unreliable test signal. If the two-test sequence is not repeatable, collect timing and environment evidence and widen the hypothesis.

06 · Practice

Fill a 20-minute isolation card

  1. Record the observer alone, suspected predecessor → observer, and the reverse order.
  2. Inventory the process, storage, resource and framework boundaries both tests touch.
  3. Name the setup owner, cleanup mechanism and expected start state.
  4. Apply the smallest repair, then complete the five-row verification matrix.
