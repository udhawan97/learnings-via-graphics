Why can a database index speed up reads but slow down writes?

An index is a maintained shortcut, not free acceleration. Match it to a real access pattern, count both sides of the trade, and verify the planner's choice.

ENGINEERING / THE BUILDER'S WORKBENCH · DATABASESFULL GUIDE: 9 MIN · PRACTICE: 20 MIN

01 · Visual model

The shortcut is another structure to maintain

Text equivalent: A table scan inspects rows until matches are found. A matching index orders selected keys with row references, narrowing candidates before row fetches. Inserts, deletes and indexed-value updates must also maintain that extra structure.

02 · Planner choice

Available does not mean useful

The query planner compares possible routes. A selective predicate—one that matches a small fraction of rows—often benefits from an index. A report returning most rows may be cheaper as a sequential scan. Statistics describe the data distribution that informs this choice.

Question shapeLikely useful evidencePossible plan
One customer among manyFew matching rows; matching leading keyIndex scan plus row fetches
Most orders in the tableLarge matching fractionSequential scan
Needed columns stored in the indexEngine-specific visibility and coverage conditionsPossible index-only scan

03 · Key design

Order the key for the access pattern

Filter and join

Start from repeated predicates and join conditions, not from a column that merely looks important.

Column order

For a multi-column B-tree, leading columns determine which query prefixes can navigate the ordering.

Coverage

Extra stored columns can avoid base-row access in some engines and workloads, but they enlarge the index.

Redundancy

Check existing keys. A longer key may already serve a shorter prefix, depending on the engine and query.

04 · Worked example

One support lookup, one reporting query

SELECT id, status
FROM orders
WHERE customer_email = 'reader@example.test';

For an invented million-row table, an index beginning with customer_email gives the planner a focused path to candidate orders. The same index may add little to an overnight query that reads nearly every order. Each insert also writes an index entry.

Success criterion: In a safe representative environment, the target lookup uses the intended plan and improves the measured read objective while write cost, storage and build impact stay within declared limits.

05 · Reality check

The build itself is part of the decision

  • A conventional index build can block writes; online or concurrent methods have engine-specific costs and caveats.
  • Stale statistics can lead the planner to estimate a poor route.
  • Wide or numerous indexes consume storage, cache and backup bandwidth.
  • High update rates can erase the benefit of an index-only design.

Do not tune from a diagram. Use representative data and the engine's plan inspection tools. Never experiment on a production path without the repository or operations process that owns it.

06 · Practice

Complete a 20-minute decision card

  1. Write the query shape and success threshold.
  2. Estimate the matching fraction and predict the plan.
  3. Record before/after plans in a safe environment.
  4. Measure a representative read and write, plus storage and build impact.
  5. Keep, revise or remove the candidate with one evidence sentence.

Knowledge check

  1. Why can an index speed a selective lookup?
  2. Why might a broad report ignore it?
  3. What cost appears on writes?
Reveal answer guidance
  1. Its ordered keys narrow candidate row references.
  2. Following many references can cost more than scanning the table.
  3. The database maintains the extra structure alongside the table.
